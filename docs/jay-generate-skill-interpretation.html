What Jay's /generate Skill Actually Is

My interpretation, written before we build our own version. Source: Jay's video "I replaced Higgsfield with one Claude skill" (youtube.com/watch?v=9C4TRbucmhQ) and my notes.

The one-sentence version

/generate is a Claude Code skill — a written instruction document — that turns Claude into Jay's personal Higgsfield: it takes a plain-English request, picks the right AI model and the cheapest provider that serves it, writes and runs a small script to call that provider's API, saves the result to one local folder, and logs the prompt next to it so nothing is ever lost.

The key insight behind it

Jay's core observation is that Higgsfield isn't magic. It's a wrapper: a company that read the API documentation for models like Nano Banana, Kling, Veo, and GPT-Image, wired them together into one website, and charges $79/month for the convenience. Since Claude can read the same documentation and write the same connection code, you can build the wrapper yourself. The skill IS that wrapper — Jay literally copied the API code snippets and docs from the providers into the skill file. You then pay only per image or video generated (often just a few cents), instead of a monthly subscription, and everything stays on your own disk under terms you control.

What it's made of

Three parts, all local:

  1. The skill file itself — a markdown document Claude reads when you type /generate. It contains the rules, the routing logic, and the API knowledge (endpoints, parameters, code snippets copied from provider docs).
  2. Model "recipe" files in a models/ folder — one per model, describing how to call it (which provider, endpoint, parameters, pricing).
  3. A local gallery dashboard — a small web page that reads one flat folder (C:/ROBO/generations/) and shows everything as a masonry grid, like Higgsfield's own gallery but on your machine. It also has saved "style" presets (click one, it copies the style prompt plus reference-image paths to reuse).

How a request flows through it

Your request ↓ 1. ROUTE MODEL Pick the model: Nano Banana 2 Lite is the default for images, Kling 3.0 the default for video; others only if named. Pick the provider: cheapest first → kie.ai, then fal.ai, then WaveSpeed. If one is down, fall through to the next. Read that model's recipe file from models/. Paid video ALWAYS gets a cost quote and waits for a "go". ↓ 2. PREP REFERENCES Load real logo / product / headshot files from generations/refs/. Logos are never described in words — always passed as actual image data. Files are uploaded to whichever host the chosen provider can fetch from (Fal storage for Fal jobs, kie.ai upload for the rest). ↓ 3. GENERATE MEDIA Claude writes a small Node script (never inline code), calls the API exactly as the recipe says, polls if the job is async, and saves the result flat into C:/ROBO/generations/ — no subfolders, because the dashboard only reads the root. ↓ 4. LOG + GALLERY logGen() writes a sidecar JSON next to each file (same base name) holding the prompt, model, references, and parameters. The dashboard picks the new file up on next refresh, and a /prompt-for command can later look up exactly how any image was made.

The guardrails (the part that makes it safe)

Because Claude will happily generate 100 images and drain your credits if you let it, the skill bakes in hard money rules:

  • A per-request budget — Jay's demo prompts said "total budget $3" and "$5", and the skill treats that as a hard ceiling.
  • Cheapest provider first — the routing order (kie → fal → WaveSpeed) exists purely to minimize cost. For example, GPT-Image-2 at 2K costs ~5¢ on kie.ai vs ~31–34¢ inside Higgsfield.
  • Cost quotes before paid video — video is the expensive category, so the skill must state the price and get an explicit yes before running.

What I take from this for our build

The skill's real value isn't the API calls — those are boilerplate. It's four design decisions: (1) cheapest-provider routing with fallback, (2) hard budget rules and cost confirmation for anything expensive, (3) one flat output folder with a sidecar JSON per file so provenance is never lost, and (4) a dumb local gallery that just reads that folder — because you can't judge visual work in a terminal. Copy those four ideas and the rest is plumbing.
