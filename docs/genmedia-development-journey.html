1. Where it started: Jay's video

The trigger was a YouTube video by Jay (Robo Nuggets), "I replaced Higgsfield with one Claude skill." In it, he demonstrates a Claude Code skill called /generate: he pastes a plain-English brief — product ads for an energy drink, a $3 budget, a spread of different image models — and Claude does everything: picks models, picks the cheapest provider, crafts prompts, calls the APIs, saves the images locally with their prompts logged, and displays them in a home-built gallery. In a follow-up prompt he takes one image he likes and, in the same session, has Claude animate it into a video and build an entire website around it.

The economic backdrop: Higgsfield, a popular AI media platform, charges roughly $49–79/month for credit-based access to models it does not own. It had also just angered users with a terms-of-service update touching who can use your generated content, and it deletes your assets shortly after you cancel. Jay's pitch was that the entire service can be recreated as a personal Claude skill on pay-as-you-go pricing, where a month of light use costs cents instead of $79, and every asset lives on your own disk forever.

2. The core insight: aggregators are wrappers

The load-bearing idea, worth stating bluntly: Higgsfield does not make the AI models. Nano Banana is Google's. Kling is Kuaishou's. Veo is Google's. GPT-Image is OpenAI's. Higgsfield read those companies' API documentation, wrote connection code, put a nice interface on top, and charges a subscription for the bundle. That is a legitimate business — aggregation has real value — but it is not magic, and nothing about it is exclusive.

One tier down sit the pay-as-you-go aggregators: fal.ai, kie.ai, WaveSpeed. They do the same wrapping but charge per generation instead of per month — one account, one API key, hundreds of models. And since they expose plain HTTP APIs, anything that can write code can use them. Claude Code can write code. Therefore Claude Code can be the aggregator's front end, with a markdown file as its instruction manual. That markdown file is the skill.

3. What we built, step by step

The finished product is deliberately small: two markdown files and one dashboard script, all in ~/.claude/skills/genmedia/.

FileRole
SKILL.mdThe instruction manual Claude loads when you type /genmedia (or just ask for media in plain words). Contains the hard rules, the routing policy, the two provider calling patterns, and the output/logging conventions.
models.mdA growing cache of verified "model recipes" — exact model IDs, input fields, and measured costs. Starts empty; every successful first use of a new model appends to it.
gallery.jsA ~100-line zero-dependency Node server. Serves a dark masonry-grid gallery over the output folder at localhost:7777 — click any item to see its prompt, model, and cost, with copy buttons.

The development sequence, compressed:

  1. Wrote SKILL.md around four design decisions borrowed from Jay: cheapest-provider routing with fallback; hard budget rules; one flat output folder with a "sidecar" JSON next to every file recording exactly how it was made; and a local gallery, because visual work cannot be judged in a terminal.
  2. Tested the kie.ai path: one image with Nano Banana 2 Lite. Worked first try; measured cost 4 credits (~2¢), about 12 seconds.
  3. Tested the fal.ai path: one image with Nano Banana. Worked; $0.039, about 6 seconds.
  4. Tested video: one 5-second Kling 2.6 clip via kie.ai. The skill's video rule kicked in — cost quoted first ($0.28), generation only after an explicit "go." Actual cost matched the quote: 55 credits ≈ $0.28, about 2 minutes.
  5. Built the gallery and pointed it at the output folder.
  6. Hardened the loop: after each test, everything newly learned (working endpoints, real prices, quirks) was written back into the skill files. The skill literally got smarter with each run — more on this in section 5.

4. How model routing actually works

"Model routing" sounds sophisticated. Here is the entire mechanism, demystified:

  1. Pick the model. Defaults do most of the work: images → Nano Banana (cheapest capable tier), video → Kling. Anything else (Seedance, Flux, GPT-Image…) only when the user names it. This is a two-line lookup table, not machine learning.
  2. Pick the provider, cheapest first. Our order: kie.ai, then fal.ai. If the first provider lacks the model or errors twice, fall through to the next. That's the whole "router."
  3. Get the model's input schema. Both providers use one uniform job envelope for every model they host — only the model ID string and the input JSON differ per model: 
    # kie.ai — same two endpoints for all models
POST https://api.kie.ai/api/v1/jobs/createTask   { "model": "<id>", "input": {...} }
GET  https://api.kie.ai/api/v1/jobs/recordInfo?taskId=...   (poll until success/fail)

# fal.ai — same URL pattern for all models
POST https://queue.fal.run/<model-id>            {...input...}
GET  https://queue.fal.run/<model-id>/requests/<id>/status   (poll)
    So the "500 models" problem collapses to two calling patterns plus a per-model input schema — and the schema is fetched from the provider's own docs at the moment it's needed.
  4. Generate, poll, download. Claude writes a small throwaway Node script per job, submits, polls every ~3 seconds, downloads the result immediately (provider URLs expire in ~24 hours), and writes the sidecar JSON.

That is everything Higgsfield's routing does, minus the web interface. When someone says a product "intelligently routes across models," this is usually what's behind the curtain: a preference list, a fallback chain, and a schema lookup.

5. The doubt that shaped the design: "you can't know every API"

Mid-build, a fair objection was raised: a short generic skill can't possibly contain the API details for hundreds of models across two providers. Correct — and the resolution is the most interesting part of the design.

The skill does not contain API knowledge. It contains a procedure for acquiring API knowledge. When Claude meets a model it hasn't used before, the skill tells it where the ground truth lives:

  • kie.ai publishes a machine-readable docs index at docs.kie.ai/llms.txt, with a markdown page per model listing the exact model ID and input fields. (The main kie.ai site blocks bots with 403s — we learned that the hard way and wrote it into the skill.)
  • fal.ai's model pages are bot-blocked too, but we found a better door: https://fal.ai/api/openapi/queue/openapi.json?endpoint_id=<model-id> returns the complete input/output schema for any of fal's models as structured OpenAPI JSON.

Fetch the schema, use it, then cache what worked — the verified recipe and the measured real cost get appended to models.md, so the next session skips the fetch. If a cached recipe ever starts failing (providers do rename things), the rule is: re-fetch the docs, don't retry blindly. The cache self-heals.

This is exactly what Jay did manually — he copy-pasted API snippets from provider docs into his skill. Ours does the copy-pasting lazily, on first use, by itself. Knowledge that is looked up cannot go stale the way knowledge that is compiled in does. Hold onto that distinction; it's the crux of the MCP discussion below.

6. Live tests and real measured costs

Nothing above is theoretical — every path was exercised with real money and the results verified on disk:

TestModel / ProviderMeasured costTime
Image (kie path)nano-banana-2-lite / kie.ai4 credits ≈ $0.02~12 s
Image (fal path)fal-ai/nano-banana / fal.ai$0.039~6 s

Useful reference points that fell out of the tests: kie.ai credits convert at roughly 200 credits per dollar; adding audio to a Kling clip doubles its price; a 10-second clip also roughly doubles it; and if your credit balance is short, the API returns a 402 with zero charge, which makes falling back to the other provider safe. Cost quoting isn't guesswork either — the skill checks the credit balance before and after every batch, so each generation's true cost is measured, logged in the sidecar, and used to enforce the budget ceiling.

Speaking of which, the skill's hard rules — the guardrails that make it safe to hand a credit card to an eager AI: a user-stated budget is a hard ceiling checked before every API call; video always gets a cost quote and waits for an explicit "go"; never generate more items than asked; never print API keys; and never trust a clean API exit — verify the file actually exists on disk with non-zero size.

7. The gallery: why media generation needs eyes

A terminal can tell you a generation succeeded; it cannot tell you whether the image is any good. Higgsfield's masonry-grid gallery is a genuinely important part of its product, so the skill has its own: a single Node script with zero dependencies that serves the output folder as a dark masonry grid. Videos play on hover. Clicking anything opens it large with a side panel showing the prompt, model, provider, cost, and date — read from the sidecar JSON — plus one-click "copy prompt" and "copy path" buttons. That last button is the bridge to the next task: copy a path, paste it into a "now build a website around this image" prompt, exactly as Jay demonstrated.

The sidecar convention is doing quiet heavy lifting here. Every media file gets a same-named .json beside it recording prompt, model, provider, parameters, and measured cost. Provenance is never lost: months later, "how did I make this?" is answered by a file sitting right next to the image. Higgsfield offers this as a feature; here it's just... files.

Media lands in a generations/ subfolder of whatever project you're working in — media stays with its project but out of your project files. (We tried "dump straight into the working folder" first; it mixed generated media into project files, and was reversed in one line. Cheap decisions are reversible decisions.)

8. The MCP question: why Higgsfield has one and we don't need one

Higgsfield ships an MCP server (Model Context Protocol — the standard that lets AI assistants call external tools), and it's genuinely useful. So shouldn't /genmedia be an MCP server too? We decided no, and the reasoning demystifies both.

Why Higgsfield's MCP earns its keep

MCP exists so that clients that cannot run code — the claude.ai website, mobile apps, other AI products — can still invoke external capabilities through typed, declared tools. Higgsfield's internals are closed; you cannot see or reimplement them. An MCP server is their only programmable surface, so of course they ship one. For them, MCP is the door into a locked building.

Why we don't need one

Our building has no walls. The skill runs inside Claude Code, which can already write scripts, fetch documentation, and call any HTTP API directly. An MCP layer between Claude and the providers would add a server process, a config entry, a maintenance surface — and zero new capability.

There's a deeper, structural reason. An MCP tool is a fixed contract: its name and input schema are declared in server code before any request happens. If Kling adds a new parameter tomorrow, the MCP server doesn't have it until a human edits the server and redeploys. The server can't read documentation; it can only execute code written in the past. Staleness is built into the shape of the thing. The skill inverts this: it ships no schemas, only the method for fetching today's schema at generation time. Compressed: an MCP server ships answers; the skill ships the method for finding answers. Answers rot; methods don't.

(Honest caveat: you could build a non-frozen MCP server with one generic generate(model, input) tool that fetches schemas itself — that's roughly what Higgsfield's does. But then you've reimplemented the skill's method inside a server you now maintain. Same behavior, more machinery.)

The decision reverses cheaply: if /genmedia is ever needed from claude.ai on a phone, or handed to someone who doesn't use Claude Code, the same models.md recipes can be wrapped in a thin MCP server in about an hour. Until that user exists, building it is speculation.

10. What this demystifies

Strip away the branding and the whole domain looks like this:

  1. Model makers (Google, OpenAI, Kuaishou, ByteDance…) train the actual models and sell API access.
  2. Aggregators (fal, kie, WaveSpeed — and Higgsfield) wrap many such APIs behind one account. Their engineering contribution is real but thin: uniform job envelopes, billing, storage, UI. The subscription ones add polish and house models; the PAYG ones add price efficiency.
  3. Routing is a preference list plus a fallback chain plus a schema lookup. Nothing more mystical is happening at any layer of this stack.
  4. An AI agent that can read docs and write code can stand in for an aggregator's entire front end. The instruction manual for doing so fits in two markdown files, and — the part worth internalizing — it improves itself, because every run's discoveries are written back into the files that guide the next run.

The $79/month question, answered: you're paying for interface polish, proprietary extras, and not having to think. All three are legitimate purchases. But the generation capability itself — the thing that feels like the product — was never theirs, and now it's yours: a skill that routes to the cheapest source, quotes before it spends, logs everything it makes, and shows its work in a gallery, for the price of the electrons involved.

Written July 31, 2026, at the end of the build session. Total spend across all verification tests: roughly $0.37 plus 59 kie credits (~$0.30) — about 67 cents to replace a subscription.
